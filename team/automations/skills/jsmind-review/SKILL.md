# jsMind Review Methodology

Review as a project steward, not only as a functional checker. Functional correctness is necessary but not sufficient.

## Project conventions

- PR titles and commit messages use English Conventional Commits: `<type>(<scope>): <subject>`.
- Suggested scopes: model / arranger / view / serialization / docs / tests / build.
- Code comments must be in English.
- Prefer citing locations in repo docs or source. If docs and code disagree, trust the code and note the difference.

## Base checks

Look for:
- Bugs, edge cases, type safety issues
- Missing or weak tests under `__tests__`
- API or behavior changes that break v1 expectations
- Performance problems in layout/rendering
- Unclear naming or docs
- CI status

## Higher-level review layers

Examine the change from these layers. Flag issues at any layer as important when they matter for long-term health.

### Explicit contracts
Does the change make key project contracts clearer and harder to break accidentally?

Contracts include:
- What files are published and their relative layout
- How different consumers load the library (ESM / CJS / UMD / classic script)
- How the CLI finds sibling artifacts
- How the Pages site is assembled

If a contract becomes more implicit, more dependent on build-script side effects, or only verifiable inside CI, treat it as an important issue even if the current code works.

### Local reproducibility and testability
Any non-trivial logic that rewrites files, validates artifacts, or assembles outputs must be runnable locally with an npm script and covered by tests under `__tests__`.

GitHub Actions workflows should stay thin orchestration. If the workflow contains sed, grep, or other content-level processing that is not also present in a tested script, flag it and require the logic to be moved.

### Product-level compatibility decisions
Changes that affect how existing users load or consume the library (script tag style, module format, global name, file names) are product decisions, not just build details.

Explicitly note whether v1 expectations are preserved, intentionally broken, or only partially addressed, and whether the decision is documented and tested.

### Future fragility
Ask: after this change, what is the most likely way a later contributor (or a future build-config tweak) will accidentally break the new behavior?

If the only protection is a brittle string match, an untested shell snippet, or tribal knowledge, call it out and suggest a more durable mechanism (test, explicit export map, shared helper, etc.).

### Scope and coherence
If the PR has grown beyond the original issue, check whether the new pieces still form one coherent contract. Large incidental expansions that leave new contracts implicit should be flagged or at least clearly called out.

## Kanban handoff pitfalls

- An on-disk field added to `JmStyle` / `JmTheme` / `JmNodeStyle` must also land in `docs/requirements/v2-data-format.md`: it owns the `interface JmStyle` block (§5.3), the 覆盖链 (§5.4) and the validation table (§9.5). This is the repo convention, not a preference — `#9`, `#18` and `#22` each updated that file in the same PR; check with `for c in $(git log --format=%h -- src/model/data/style.ts); do git show --name-only --format="" $c | grep -c v2-data-format; done`. `docs/requirements/v2-cli.md` is the opposite case: it is a design doc no CLI implementation PR has ever updated, so a missing new command group there is a note, not a blocker (and it already says `render` where the CLI has `export`).
- A help block copied from a sibling command: run the flags it names. `mind set-style --help` (renamed from `mind style set`) inherited `node set-style`'s "A dot marks a level, so --node.radius addresses `style.node.radius`" sentence, but only `node`'s `STYLE_FIELDS` contains dotted flags — `--node.radius` exits 2 with `Unknown option`. Compare the example in the help prose against the actual field table before trusting either.

- The PR title is history, not decoration: repo squash settings are `squash_merge_commit_title = COMMIT_OR_PR_TITLE`, so any PR with more than one commit squash-merges under its **PR title**. A stale title (wrong type, or describing an approach the rework removed) writes a false commit subject into master — that is a must-fix on its own, even when the diff is correct. A single-commit PR takes the commit subject instead, so check `git rev-list --count origin/master..HEAD` before deciding.
- `team/automations/weka/github-webhook.py` is run by a systemd **user** unit straight out of the main checkout (`ExecStart=%h/repos/jsmind-v2/team/automations/weka/github-webhook.py`) with `Restart=always` — restarts on exit only, never on file change. Merging a fix to that script changes nothing until the main checkout is pulled and the unit restarted, so the README needs that step documented (the procedure now lives in `team/automations/skills/weka-deploy/SKILL.md`); verify with `systemctl --user status github-webhook.service` (uptime older than the commit = old code live).
- Audit the deploy step itself against the host, not just its presence. `git -C ~/repos/jsmind-v2 pull --ff-only` is wrong when the main checkout sits on a stale feature branch: `git status -sb` shows `[gone]`, `git ls-remote --exit-code origin refs/heads/<branch>` exits 2, and `pull --ff-only` fails with "specifies to merge with the ref … but no such ref was fetched" (exit 1) — while the next line `systemctl --user restart` ignores that and reloads the OLD code, reproducing the silent no-op the doc exists to prevent. Require `switch master` first (or `&&` between pull and restart) plus a `log -1 --oneline` that proves HEAD moved.
- `SOUL.reed.md` / `SOUL.cody.md` are deployed as **copies** into the profiles (`~/.hermes/profiles/<p>/SOUL.md`), so a PR that edits them changes nothing live until they are re-copied. Check with `diff ~/.hermes/profiles/reed/SOUL.md <(git show origin/master:team/automations/weka/SOUL.reed.md)`; identical output means the merged SOUL edits never reach the running agents, and the README's pull+restart note does not cover it.
- A close-time label fallback only fires on future `closed` events. Enumerate the residue it cannot reach with `gh api 'repos/{owner}/{repo}/issues?state=all&per_page=100' --jq '.[] | select(([.labels[].name] | map(select(startswith("weka-"))) | length) > 0) | {number,state}'` — closed issues still carrying `weka-working` stay that way, so either say so in the doc or prescribe a one-off `gh issue list --state closed --label weka-working` cleanup.
- `issues.closed` deliveries leave no journal trace under the pre-close-time-fallback code (the handler returned before printing), so a service journal only proves the `pull_request.closed` half of the subscription. Cite the `Issues` subscription being demonstrably live (`issues.opened` cards) rather than claiming to have observed `issues.closed`.
- A rework card's implementer is barred from editing the PR title/body (`team/automations/weka/SOUL.cody.md`: 返工卡「不要改它的标题和 body，只推代码」), so a stale body after rework is not implementer negligence — the reviewer must ask for the sync explicitly and say it overrides that rule, otherwise the body stays wrong and the next round repeats.
- A usage error that enumerates its accepted values from a shared table outlives the removal of one value. When a narrower parser is layered on top (`parsePlacementSide` over `parseSide`), the inner one's `must be one of left, center, right` keeps advertising the word the outer one now rejects — so the hint sends the caller to a guaranteed exit 2. Probe with a *bogus* value, not only with the deliberately-rejected one; the rejected value's own message is usually the correct, explicit one.
- A plain-object lookup table indexed by a command-line value resolves `Object.prototype`: `SIDE_SYNONYMS['constructor']` (also `__proto__`, `toString`, `valueOf`, `hasOwnProperty`) is not `undefined`, so the "unknown word" usage error is skipped and the junk value only dies later in post-write validation as a data error (exit 1, `E_SIDE … got undefined` / `got {}`) instead of exit 2 with the candidate list. Probe the prototype keys, not just a plausible typo like `middle`, and fix with `Object.hasOwn(table, raw)` or a null-prototype table — or reuse `enumOption()` (`src/cli/io.ts`), which uses `allowed.includes`.
- A "three copies of one surface" parity test only protects the direction it asserts. A test that looks up two rows' option strings in the guide tables does not notice a *retired* command re-appearing as an extra row — the exact drift its own comment cites. Check that absence of the removed name is asserted in every copy, not just that the surviving rows match.
- When a PR claims "help matches both doc tables verbatim" but the test pins only the rows it changed, re-verify the WHOLE table yourself: flatten the help block (`re.sub(r'[ \t]+', ' ', help)`) and match each doc cell token-by-token in order. A plain whole-cell substring check reports false DIFFs because the help block puts the description column *between* a wrapped option list (`add-child --parent-id … --text … <desc>` / `[--side …] [--position …]`), so wrapped rows look absent when they are fine.
- Auditing a "method ↔ CLI command" doc table: check which model method the command actually calls (`grep -n 'mind.addNode(' src/cli/commands/mind.ts`), not just whether the row's option string is plausible. After a merge like add-node→add-child the surviving old row can keep flags the method it names cannot express; with §3's "semantic mapping, implementation decides" preamble that is a note, not a blocker.
- In single-query mode the terminal parser blocks heredocs, so `gh pr comment --body "$(cat <<'EOF' …)"` is refused as dangerous: write the comment into the scratch workspace with `write_file` and pass `gh pr comment --body-file <scratch path>`.
- A PR that widens what a CI output flag means (`docs` now also covers `skills/`, `library` now covers non-markdown under `skills/`) must update every place that *describes* the flag, not just the classifier: the `outputs:` block at the top of the workflow, the step's comment block, the diagnostic `echo`s, and each job header that states its trigger. Grep `grep -n 'docs/\|markdown\|prose' .github/workflows/ci.yml` and check every hit against the new `case` branches — seen `outputs: docs` still defined as "at least one changed file is under docs/" and a `library` rule comment saying "outside docs/ and skills/" while the new `skills/*)` branch sets `library=true` for non-markdown. The wrong rule comment is the dangerous one: a later maintainer editing the classifier to match it would delete the library checks the PR exists to preserve.
- A whole-directory `cpSync(src, dest, {recursive:true})` placed *before* a per-file existence check throws raw `ENOENT: … cp '<src>'` when the directory itself is gone; only the empty-directory case reaches the curated `missing or empty site file: <path>` message. Probe both (delete the dir, then empty it) and treat the missing-dir case as a message-quality note, not a build failure — both fail the build.
- Accepting "the published URL opens as the original file" without deploying: GitHub Pages serves `.md` as `text/markdown; charset=utf-8` (check any live `*.github.io/**/README.md` with `curl -sSI -o /dev/null -w '%{http_code} %{content_type}'`), and Chromium renders that inline as plain text rather than downloading — serve the file locally under that content type and read `document.contentType` + `document.body.innerText`, which is the whole acceptance claim.

- Loosening the CLI's `parseArgs` from `strict: true` to `strict: false` drops **three** checks, not the two a PR usually restores (missing value, value that looks like a flag). The third — "Option '--json' does not take an argument" — leaves every boolean flag accepting `--dry-run=true` / `--json=1` as a *string*, and since commands compare `values['dry-run'] === true` the flag is silently ignored: pre-PR exit 2 becomes exit 0 **with the file written**. Probe `--dry-run=1 node set-text …` and compare sha256; `--version=1` also falls through to help. Require the boolean branch in the `assertOptionValues()`-style shim plus a table case. When it lands, verify the restored message against `parseArgs({strict:true})` on the same flags — it should match `ERR_PARSE_ARGS_INVALID_OPTION_VALUE` byte for byte — and grep the repo for `--(json|dry-run|backup|strict|version)=` before accepting that no legitimate caller used the lenient form (this round: only the tests that assert the refusal).
- In `node:util` `parseArgs` lenient mode an unknown short option is keyed by its letter (`-z` → `name: 'z'`), so a warning that prints `--${name}` tells the caller to fix `--z`, a flag it never typed — matters in a repo whose policy is "no spelling suggestion".

- When a rework deletes something the PR body still describes (script, test, flag), audit the body as part of the deliverable. This repo squash-merges with `COMMIT_MESSAGES`, so a stale body does not reach git history, but it stays the PR's public record and misleads the next reader about why that check no longer exists. A body-only fix is a legitimate `kanban_request_changes`; say explicitly "no file changes this round".
- Counting skill-copy parity by hand after the parity script is removed (there is one skill file, `skills/jsmind/SKILL.md`; the Chinese copy was deleted, so a table of "the pair" is itself a stale-fact trap): in single-query mode python heredocs and `execute_code` are blocked, so use plain grep — `grep -cE '^#{$lv} '`, `grep -c '^```'`, `grep -c '^    \$ '`. Read the counts off the file each time; never carry a copied line-count into a review, they go stale within a merge or two.

- Probing a workflow's inline shell classifier: `sed -n '<first>,<last>p' .github/workflows/ci.yml` into a scratch file and `source` it with `changed`/`GITHUB_OUTPUT` exported is the fast path — but size the range by the last `echo "<name>=$…" >> "$GITHUB_OUTPUT"` line, not by the closing `fi`. Cut at the `fi` and the script prints an empty output block that reads like "no finding" for every scenario; re-extract (this file: `changes` needs 128-190, `docs-site` 357-389) and confirm the four/two output lines appear before trusting any verdict.
- A worktree has no `node_modules`, so `pages-site` runs 8/9 (the VitePress case dies on a missing binary) and looks like an environment-only gap. `ln -sfn <main>/node_modules ./node_modules` makes it 9/9; the symlink shows as untracked in `git status` because the ignore pattern ends in `/`, which is harmless but do not let it into a commit.
- Verifying the docs-site half of an install URL means comparing the live bytes to the repo, not just the status code: `curl -sS https://hizzgdev.github.io/jsmind-v2/skills/jsmind/SKILL.md | sha256sum` against `git show origin/master:skills/jsmind/SKILL.md | sha256sum`. Equal hashes prove the deploy tracks master, so a new prompt URL starts serving the new file the moment the PR deploys; a mismatch means an older deploy, not a broken URL. `references/*.md` and `tests/*` answer 200 as well — a 404 there is a filename you invented, so read `ls skills/jsmind/` first.
- A prose assertion that only `readFileSync`s a markdown file can be reverse-tested with no `node_modules` (and no VitePress): replicate the test's exact regex in Python and run its predicates over mutants — prompt grown a second line, URL swapped back to `raw.githubusercontent.com`, fence stripped, whole section deleted. Baseline passes and every mutant trips at least one predicate is the non-vacuity proof the CI job cannot give (it only runs the passing direction). Heredocs are blocked in single-query mode, so `write_file` the probe into the scratch dir and run `python3 <path>`.
- On a worktree whose branch is behind master, `git diff origin/master HEAD` lists files the PR never touched — seen `skills/jsmind/SKILL.md` after #146 merged since the branch point, reading as `mind style set` vs `set-style`. Use `gh pr diff` or `git diff $(git merge-base origin/master HEAD) HEAD` before concluding the PR drifts into an unrelated file.

- Probing a content check (`check-version-refs`, `format-check`, EOF newline) by appending a sample line: reset the sandbox to a clean tree first (`git reset --hard HEAD` and assert `git status --porcelain` is empty) before every variant. A probe appended onto a leftover edit reports the leftover's violation, so exit 1 looks like proof for the new line when it is the old one — and exit 0 can hide that the new line was never the only thing scanned. Read the `file:line` from the report, not just the exit code.
- A new spec or conventions doc whose examples name CLI subcommands, API fields or table locations: `git grep` every identifier in the examples. Illustrative examples are part of the deliverable, and an invented name in a doc advertised as the single source of truth is a must-fix, not a nit — seen `jsmind tree` (never exists; the CLI has `context` / `validate` / `export` / `convert` / `mind *` / `node *`), `JmNodeStyle.borderRadius` (interface has `borderColor` / `borderWidth` / `borderStyle` / `fontSize`), `jsmind render` (renamed to `export` by the spec itself), and a "CLI 子命令表 … 加一列" pointing at a table `v2-cli.md` does not have (commands live in §5 sections).
- Accepting a boundary the owner left ambiguous: when a code exemption is narrower than the owner's wording (only `Since:` exempt vs "abolish the whole triple ban"), probing both sides proves the *implementation* works but not that it is what was asked. Never carry that as a blocker; state both readings with their cost and ask the owner for one line on the PR, then let the merge decision sit with them while the technical verdict proceeds on everything else.

- "Literal `X` is rejected" doc claims need the exact string tried, not the shape. `check-version-refs.mjs` matches `\b2\.\d+\.\d+\b`, so the placeholder `2.x.y` passes (letters) while `2.1.0` fails: a doc saying `2.x.y` 这种字面量会被拒 is describing the `N.N.N` shape, which matches repo idiom (ci.yml comment uses `2.0.x`, npm-release.md uses `jsmind@2.x.y`). Report the mismatch as a non-blocking wording note, not a round of rework.
- Docs that document install + acceptance commands: check that every acceptance command actually runs on every install route the doc offers. `docs/*/guide/skill.md` offered `npm i -g jsmind@2` *or* `npx jsmind@2`, then listed bare `jsmind --help` as acceptance — an agent on the npx route fails all three checks with command-not-found, the exact misdiagnosis such a guide exists to prevent. Also grep the install command against the rest of the repo (`README.md`, `docs/*/guide/getting-started.md`, `team/development/npm-release.md` §1.1): a single guide using `npm i -g` where everything else uses `npm i jsmind@2` + `npx jsmind` is an undocumented contract split.
- Acceptance commands also depend on the working directory: `npx jsmind` outside the tree where `npm i jsmind@2` ran falls back to registry `latest` = 0.9.1 and exits with `npm error could not determine executable to run` — the same string a doc blames on `npm i jsmind`. Any install file that quotes that error must also say to install in (or above) the directory you will work in, else the agent misdiagnoses again.
- Docs-only PRs get a thin CI: `.github/workflows/ci.yml` gates `type-check`, `test:coverage` and `build` on `needs.changes.outputs.library == 'true'`, so a PR touching only `skills/`/`*.md` shows a green "Format, types, tests, build" check in ~15s that ran format-check and nothing else. Test counts and coverage figures in such a PR's body are therefore NOT CI-verified — either run `npm run test:coverage` once locally or say in the review that CI cannot reproduce them.
- Coverage percentages can drift in the last decimals between machines/retries (seen: body 96.43/93.13/95.73 vs local 96.44/93.24/95.73 twice on the same SHA). Record the measured value on the PR as a non-blocking note; do not spend a rework round on 0.01%.
- Clearing the assignee (`hermes kanban assign <task> none`) is impossible from a kanban worker: the CLI is fenced (`kanban_path_is_fenced` -> "delegate_task child contexts cannot mutate Kanban tasks via the CLI"). Do not try to work around it. After posting the review on the PR and adding the repo owner as reviewer, finish the card with `kanban_complete`; that is the review lane's terminal action and it stops the dispatcher from re-spawning you. Leaving the card in `review` while assigned loops you forever.
- Dry-running a documented `gh api` snippet: put a `gh` shim first in `PATH` that prints and swallows every write verb (`-X DELETE|POST|PATCH|PUT`), never sed-replace one command. Replacing only the `-X DELETE` in `SOUL.reed.md`'s label block let the neighbouring `gh api -X POST ... -f labels[]=weka-reviewed` run for real and tag four live PRs; it had to be rolled back. The shim must sit on `PATH` (the real binary is `/usr/local/bin/gh`, a symlink) and read calls must still reach the API so the probe reflects real state.
- Probing a documented shell block: extract the fence verbatim with python `re.findall(r"```bash\n(.*?)```")` (awk heuristics silently drop the first line, e.g. the leading `cd … &&`) and run it with `git`/`systemctl`/`gh` **stub** scripts first in `PATH`, then assert the `&&` chain stops when a middle step fails. A trailing `# comment` after `&&` is legal bash, so the multi-line form `cd x &&\n  git switch master &&   # c\n  git pull …` works — prove it, don't read it.
- Those stubs persist in the terminal session's `PATH` across calls and break later `node` scripts that `execFileSync('git')` — `npm run format-check` then dies with `spawnSync git ENOENT`. Rebuild `PATH` explicitly (or use a scratch sub-shell) before running any npm script.

- `gh api -X DELETE .../labels/<absent>` returns 404 + exit 1 — it is NOT idempotent, contrary to what `SOUL.*.md` used to claim (both files were corrected since; re-read the block before citing a line number, that claim has moved).
- That existence guard swallows read failures: if the label *list* call errors (auth, network, 404 repo), `grep -qx` just makes the pipeline false, the branch is skipped, and the whole snippet exits 0 even under `set -o pipefail` (a failing `if` condition does not trip `set -e`). So "clean" and "could not check" look identical — a stale label survives silently. Report it as a non-blocking note unless the doc explicitly promises otherwise.
- `gh` resolves the WRONG repo once the worktree is gone (post-completion cleanup) — a bare `gh pr view 86` then hits whatever repo the cwd maps to. Always pass `-R hizzgdev/jsmind-v2` when verifying the PR after completion.

- A docs PR whose body quotes a test count is quoting the *branch*; CI runs the PR merge ref. On a branch behind master the two differ (body `524 pass`, CI `ℹ tests 530 / pass 530` from #146's tests). Pull the number out of CI instead of trusting the body: `gh run view <run-id> --log --job <job-id> | grep -a '# pass'`, and confirm the changed test file actually ran by finding its row in the coverage table (`pages-site.test.ts | 100.00 |`). Note the mismatch as non-blocking — the branch number is true, just measured on a different tree.
- An install doc that offers a mirror as a fallback can be handing out a copy that predates the very frontmatter its checklist reads. Fetch the mirror URL and compare against `git log` sizes: `gitee.com/.../raw/master/skills/jsmind/SKILL.md` served 18949 B = master `35592fd`, a version with no `version:` and no `metadata.jsmind.cli`, so "compare the CLI against the `cli` range in frontmatter" was unrunnable for the github-blocked reader the fallback exists for. Gitee raw answers `text/plain` (not `text/markdown` — harmless, bytes are bytes) and lags by whole revisions, not just commits. Report it as a note when the doc already says the mirror lags and to identify which copy you hold; it self-heals on the next sync.
- `raw.githubusercontent.com` is unreachable from this host (curl exit 35, `SSL_ERROR_SYSCALL`), so anything that only checks the GitHub raw half of a dual-source doc has to be proven through `gh api`/`git show origin/master:...` instead. Verify the Gitee half over HTTPS, which works.

- A PR body that says `Closes #N`: enumerate the issue's deliverable checklist and count the items, don't map "the files this PR touches" onto "the issue's scope". An issue can list four or five bullets while the PR covers two; three review rounds can ratify "2 files, no third file, compliant" purely because nobody counted the checklist, and the merge then closes the issue with empty boxes. Either require the missing deliverables or require `Refs #N`.

- A content check that strips a pattern before matching (e.g. `Since: N.N.N`) and then reports `line.trim()` of the *stripped* string shows the reader a line that is not in the file. Probe one line containing both an exempt marker and a bare triple and read the reported text, not just the exit code.

- `gh api -X DELETE .../labels/<label> --jq '.name'` errors with "expected an object but got: array" (DELETE returns the remaining label list) while the delete itself succeeded — re-read the label list instead of trusting the exit code.

## Error-path messaging pitfalls

- Recovery instructions printed on a failure are deliverable code, and they are testable: replay them literally in a scratch clone. `git checkout -- <paths>` restores from the **index**, so a hint that says that after the script already ran `git add` undoes nothing, and a following `git checkout master` carries the staged version bump onto master — the exact "version change that skipped its PR" the release flow exists to prevent. The correct undo for the staged case is `git restore --staged --worktree <paths>`. Same-shape checks for the other branches of the same script: hints printed *before* any `git add` are fine, so only the post-add one needs fixing.
- `scripts/verify-npm-pack.mjs` (`npm run pack:check`) asserts the tarball lists the nine `dist/` files, and `dist/` is gitignored — on a clean tree it exits 1 with `Missing: dist/cli.js ...`. Anything that runs `pack:check` as a release step (`release:prepare`) therefore fails on a fresh clone after it has already bumped the version; check that path, not just the dry run, and note it as a hint-quality issue rather than a blocker.
- Probing the release scripts needs a repo that can push history: the task worktree is often a shallow clone (`git push` there fails with `shallow update not allowed`). Build the sandbox from `git archive <sha> | tar -x -C work`, `git init -b master`, commit, push to a bare origin, and put a `gh` stub first in `PATH` answering `run list` (headSha/status/conclusion of the sandbox HEAD) and `repo view`. Then dirty / behind / tag-present / happy paths are all reachable offline. Rebuild `PATH` afterwards — the stub shadows the real `gh` in later calls.
- Release-script preflights read tags with `git tag --list` after only `git fetch origin <branch>`; bare fetch does not follow lightweight tags, so a clone whose tags lag silently produces a release-notes range starting at an older tag. Worth a note unless the script fetches tags or reads `ls-remote`.
- Release-version assertions must be checked for accidental satisfaction: build the docs yourself (`node node_modules/vitepress/bin/vitepress.js build docs --outDir <scratch>`) and grep the built home page for the version string. If it occurs exactly once and only inside the injected block, `html.includes('v' + version)` really does fail when the block is removed; if it also appears in a nav or changelog snippet, the assertion is decorative.

- A home-grown semver range check needs a range/version table, not the shipped range plus one reverse probe: `/^(\d+)(?:\.(?:\d+|[xX*]))?(?:\.(?:[xX*]))?$/` silently reads `2.3`, `2.3.x` and `2.3.*` as "any 2.x" (`tokenComparators` in `scripts/check-skill-meta.mjs`), so `cli: "2.3.x"` against package.json 2.0.1 exits 0 and prints "covers" although semver puts 2.0.1 outside `>=2.3.0 <2.4.0` — a check whose header promises "refuses anything else loudly". Probe `>=`/`>`/`<=`/`<`/`=`/`^`/`~`/x-range/intersection plus `||` and hyphen ranges, and require a `__tests__/build/*.test.ts` next to `version-refs.test.ts` for any new content check: that script's `ROOT` comes from its own path, not cwd, so the version-refs harness (cwd → mkdtemp repo) cannot be reused as-is — the script has to be copied into the temp tree or given a `--root`/cwd parameter. Once it has `--root`, stop enumerating by hand: `node_modules/semver` is already present as a dev dependency, so drive the script over range × version (22 × 17 is enough) and diff every verdict against `semver.satisfies(v, r, {includePrerelease:true})`. Documented refusals (`unsupported range syntax`) count as agreement only for shapes the header calls unsupported — e.g. `1.x.3` refused while semver reads it as an x-range is the conservative legal choice, not a bug.
- `context --json` is the skill's own contract, so verify its fields rather than the prose: on the built `dist/cli.js`, `add-child --position 0 --folded true` lands first and prints `(folded=true)`, `mind set-style --default-tone primary` makes `style: {theme, defaultTone, overrides: ["defaultTone"]}` appear, and a toned node carries `style: {tone}` while a folded one carries `folded: true`.
- In `check-version-refs.mjs` the frontmatter exemption matches `^skills\/.*\/SKILL\.md$` while `check-skill-meta.mjs` reads only `skills/jsmind/SKILL.md`: a second skill's `version:` would be exempt from both. Probe it by writing `skills/probe2/SKILL.md` (mkdir first) and note the gap; prose is still scanned (a `2.7.9` in the body or in the `description` block scalar is reported with its real line number).

## Rendering acceptance items

- An acceptance bullet that says "after setting X, export looks like Y" is provable without eyes: `jsmind export <file> <out.png>` twice and compare. Build a control document where every node states explicitly what the feature supplies as a default — if a doc-level `style.defaultTone = primary` renders **byte-identical** to the same map with `tone = primary` on every node, the fallback provably reaches both painters. Then add one node with an explicit different tone and show only its own line colour changes.
- Counting palette pixels needs no PIL here: a ~40-line stdlib script (`zlib` + PNG unfilter for bd=8, ct=2/6, interlace=0) yields a colour histogram. Compare against the hex values in `JSMIND_THEME_DEFAULT` (`src/model/data/style.ts`): `fillColor` / `lineColor` per tone. `#b0b0b0` (default tone's lineColor) at 0 px is how you prove lines stopped using the default tone.
- Chromium is at `/usr/bin/chromium-browser`; export works without `CHROME_PATH` and takes ~2s per image at 600x400.

## UI review pitfalls

- The UI harness (`__tests__/ui/helpers.ts`) launches Chromium with `--hide-scrollbars`, so any element-width comparison in a UI test is blind to scrollbar gutters: `clientWidth` assertions pass whether or not the gutter is reserved. Verify scrollbar-dependent geometry yourself — serve the worktree (`python3 -m http.server`) and launch `/usr/bin/chromium-browser --headless=new --remote-debugging-port=...` **without** that flag, then read `div.offsetWidth - div.clientWidth` to prove the browser reserves space (15px here), and compare both layers' `clientWidth` plus `scrollHeight` on long wrapping lines. `scrollbar-gutter: stable` does apply to `overflow: hidden` elements in Chromium.
- A layered editor (transparent textarea over a highlight copy) has geometry the suite can only partly see. `scrollHeight` equality proves line count, not caret placement; take a `Page.captureScreenshot` at `deviceScaleFactor: 2` with the caret placed by `setSelectionRange` and look for doubled glyphs, missing token colours, and a caret drawn outside its line.

## Priority

Lead with the highest-layer issues. A change can be functionally correct and still deserve a request-change if it weakens long-term contracts or testability.

Write reviews in simple, short English. Prefer concrete suggestions over general advice.
