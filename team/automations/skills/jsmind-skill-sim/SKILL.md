# jsmind skill 模拟测试

## 什么时候用

跑 jsmind skill 的模拟测试时装载：八轮真实操作，最后产出一张卡点表和一份提案。不是用来自己画
图的——画图是 jsmind skill 的活，在仓库里为了干活而装载这个文件，是 runner 的错。

`tests/` 下那两个 fixture 测的是一轮之内的事；这个文件测的是一段会话：八轮连续的修改，中间有
快照、有反复、有前一轮埋下的坑。两者都跑，才知道 skill 是"单题会做"还是"能干活"。

## 你是谁

你是被测对象。被测的是这个 profile 里已有的 jsmind skill，不是你自己的能力——一轮走得很顺，因为
它本来就会，这也是数据；但一轮里它猜对了，才是更有用的数据。

工作目录里只有输入的地图和你要产出的文件。没有项目源码、没有文档、没有 git 历史、也没有 issue
库，也不许去抓：答案就在那里，打开就等于实验结束。某条命令因为路径或参数不存在而失败，那是一条
观察记录，不是靠去别处找答案绕过的问题。

`jsmind` 已经在 PATH 上，已经能用。这次测的是**使用**，不是安装：不要装、不要升级、不要重装、不要
核对版本，也不要碰 npx、npm 或者仓库。它要是缺了或坏了，那是这次运行的问题，不是任务——说一声
然后停。

## 什么算一条卡点

一条卡点（friction）是：**为了完成这一轮，你必须有某个信息，而 skill 没有在你要用的那个位置给
出它，于是你猜了一把、试了一下、去读了 `--help`、重试了，或者绕了远路。**

不算卡点：图要敲好几条命令（那是活本身）、你自己慢、两秒钟就修好的拼写错误。最后一种里有一类
要单独记：凡是因为读了 `jsmind --help` 才解决的，不计入卡点，单列一节——它是最重要的信号，说明
skill 在该处没有回答。

任何时候都可以去读 `--help`。每次都要记：敲了什么命令，以及帮助页告诉了你什么、而 skill 没告
诉你的。

## 步骤

按顺序做。一轮一轮来：命令跑完、`validate` 通过、导出 png 并看过一遍、报表里有这一行，这一轮才
算完。（R7 不写文件。）

**快照纪律**：`rN.json` 必须是这一轮**最后一次写入之后**的副本。复制、`export` 之前先比一次
`md5sum map.json rN.json`，两个值必须一样；不一样就是复制早了，重来。历史上有人在这一步上翻了
车：拿折叠前的旧副本导出，得到的图自然和上一轮一模一样，于是判定"renderer 忽略折叠"——那是测量
错误，不是缺陷。

### R0 建图

> 帮我画一张太阳系的脑图：根节点叫"太阳系"，八大行星按离太阳从近到远依次挂上去。

八个一级分支，超过 skill 建议的七个。你怎么处理——照建八条，还是先问——都记下来：skill 怎么说、
你怎么选。左右怎么分配也记，因为它在 add 的那一刻就定了。

### R1 加一个，再改刚加的那个

> 在地球下面加一个月球，然后把它改名成"月球（卫星）"。

改名要用的 id 应该直接从 `add-child` 的回显里拿。如果你绕回去再跑一次 `context` 找这个新节点，
那是一条卡点，写清楚。

### R2 整张图，再改单个节点

> 整张图的颜色统一调一下，再把地球改成蓝色。

一句话里两个层级：文档级默认色，再给一个节点上色。记它写了几次——八个行星各写一次样式，而不是
一条文档默认，就说明"优先级"那条没落地。再记"蓝色"它用了哪个字段：`tone`、`background` 还是
`color`。用 `tone` 的，记那个 tone 跟文档默认是否同一个（同一个就等于没改，图上什么都不会变）；
用原始颜色的，记它改的是方块还是字，以及字和方块叠在一起还看不看得清。

### R3 缩小画面，不改数据

> 现在只想对比地球和火星，把其它行星都收起来。

这一轮之后，文件只应该多出折叠标记：地球和火星展开，其余收起。删除是 R4 的活——你要是这一轮就
删了，写出来。

导出可以看一眼，但别指望画面有变化：当前图里除了地球，其它行星都是叶子，折叠叶子不会改变画面，
所以 PNG 可能和上一轮一模一样，这不是缺陷。要验"折叠真的收起了子树"，得折一个有子节点的分支
（这一轮只有地球有），那和"只留地球火星对比"冲突，所以这一轮只验文件里的 `folded` 标记。

### R4 删除

> 把其它行星都删掉，只留地球和火星，太阳不动。

删一个节点会连它的子树一起走。确认地球下面的月球还在，并记下你确认了什么。

### R5 填细节

> 把地球和月球的参数列得详细一点：直径、离太阳的距离、公转周期各一条，月球再加一条离地球的距离。

这句话有两种读法，都合法：三项只给地球（4 个新节点），或者两个天体各三项、月球再加一项（7 个）。
你要哪种都行，但要写清你按哪种理解做的——这不计卡点。

这是批量场景，记它敲了几条命令，以及 skill 里有没有哪句话暗示了一条并不存在的捷径。

### R6 给剩下的重新上色

> 把火星改成红色。

跟 R2 后半句是同一条路，隔了三轮，而且文档级默认色已经在位。如果它只写了一个节点样式，记下它是
不是先又去读了一遍 `context`——它要的 id 在 R3/R4 里已经碰过。

### R7 只读

> 这张图现在讲了什么，有几层？

R7 里不该有任何改文件的命令。改了就是一条卡点。答"几层"要用能看见全树的命令，别让默认深度截断
了答案。

## 你要产出什么

三样东西，放在工作目录根下。

### 1. friction.md

一条卡点一行；就算某一轮没有卡点，也要留一行写 `none`。

表格之前先写三行来源，数字分别取自两个 `SKILL.md` 的 frontmatter 和 `package.json`：

```
skill:   jsmind <version>   (<commit sha，或 working tree>)
cli:     <jsmind --version 的输出>
sim:     jsmind-skill-sim <version>
```

理由：两次运行如果被测的 skill 不是同一个版本，两张卡点表就不可比——diff 出来的差异分不清是
skill 改好了，还是换了被测对象。

```
| 轮次 | 用户原话 | 敲过的命令（按顺序，含失败的） | 第一次就成 / 失败(退出码 N) | 卡住时做了什么（猜 / 读 help / 重试 / 放弃） | 以为会怎样 | 实际怎样 | skill 在哪里回答了（行号或原文，或 none） | 这一轮结束时的状态（validate / 四检） |
```

"skill 在哪里回答了"这一列最要紧。填行号，说明 skill 本来有答案、只是要翻；填 `none`，说明它没
有。两种缺陷，改法不同。

表格下面再写 `--help` 记录：每一次调用，以及它回答了 skill 没回答的什么。

### 2. proposals.md

一条卡点一个块，格式固定。不许自由改写 skill。

```
friction:     R2 —— "整张图统一调一下"没说清是文档级还是节点级，只能猜
location:     SKILL.md <哪一节>，<哪句或哪个空位>
before:       <原文，或者"(这里没有)">
after:        <替换文本，或者要加的那行>
kind:         promote-to-step / fix-wrong-advice / add-line / delete
assumption:   下一个 agent 读到这句时，手上正拿着什么
risk:         这个改动会破坏别的什么任务
```

另外必须做一件事：给每条卡点标出"本该回答它的那句 skill 原文"，或者 `none`。这是整份报告里最便
宜的诊断——卡点全是 `none`，说明结构有缺口；卡点全都能映射到具体句子，说明位置不对。两种改法完
全不同。

不要改 jsmind skill，不要改任何命令或源码。如果你认为 CLI 本身有问题，单独写一个标题说明——那
不是 skill 的修复，这次运行也不处理；而且**在写进去之前先自己复现两遍**：换个文件名、换个目录再
做一次，确认不是快照顺序或者自己的脚本把结论带歪了。

### 3. 产物

每一轮之后：当时的 json（`r0.json` … `r6.json`），以及每次导出的 png（同样编号）。都留在工作目
录。它们是"图没问题"这种说法的核对依据，也是下一次运行跟这一次对比的基准。

## 谁来写修复

你提案，runner 落笔，另一个人验证。不是说提案不对——提案是原材料——而是有四件事在这一轮里看不
见：

- 你看得见自己卡在哪，看不见下一个 agent 会花多少注意力才放弃。
- 卡点之后的反射是解释它，而解释会让一页可能已经因为太啰嗦而失效的文档更啰嗦。
- 你没有对照组：凑巧成过一次的写法会变成"标准答案"，哪怕同一个命令有更省的形式。
- 你验证不了自己写的修改。在已经知道坑在哪的上下文里读，怎么读都是绿的；那不是修好了，是假绿。

## 停手并汇报

R7 答完就停。不要多跑一轮，不要顺手把图改好，不要把提案整理漂亮。把发生过的事都写下来，包括那
些很顺的轮次：skill 在哪一轮好用了，那是下一次迭代不该破坏的东西。

## Runner 准备（不是被测者的说明，交接前把这节删掉）

- 全新 profile；skills root 下只有两个技能：锁定 sha 的 `jsmind`，和这一份。仓库里它在
  `team/automations/skills/jsmind-skill-sim/`，装法是把整个目录拷成
  `<skills root>/jsmind-skill-sim/`
  ——目录名就是 skill 名，SKILL.md 必须在那一层，塞进 `jsmind/tests/` 之类的地方就不算 skill。
  不要有任何别的可能回答项目问题的东西。
- 工作目录：只做修改的跑法给一张输入图；建图的跑法给空目录；不要有仓库检出。
- CLI 用 `npm i -g jsmind@2` 装，装完 `command -v jsmind` 必须非空，再跑
  `jsmind --version` 确认是 2.x。**不要手工打包 `dist/` 塞进 `node_modules`**：tar 会带走文件权
  限，`dist/cli.js` 变成 644，`node_modules/.bin` 的软链就不可执行，接着整轮都被这个环境问题污
  染。版本号记进运行日志；被测者不装、不升、不查，也不要把 `npx` 当成调用方式交给它——npx 是下
  载路径，网络一慢就会变成一条跟 skill 无关的卡点。
- 轮次可以一轮一轮外部喂，而不是从本文件读——外部给的 prompt 优先于这里的文字。外面喂能避免轮次
  之间互相污染；从文件读测的是一整个上下文里的完整流程。
- 把 `friction.md`、`proposals.md`、`map.json` 和产物归档到 `runs/<日期>-<sha>/`，两次迭代才好
  对比。
- 跑完之后：每条自述卡点都先当命令重放一遍再信，然后归成"skill 缺失 / skill 说错 / CLI 缺陷"三
  类。只有前两类进 skill。凡是自述"CLI 缺陷"的，先怀疑被测者自己的测量方法：快照顺序、md5 比错
  了文件、拿旧副本导出，这三种比真缺陷常见得多。
- 落了提案之后的复测是**新 profile、新上下文**，绝不用刚跑完的那个 agent：它已经知道坑在哪，不会
  再踩，它说的"修好了"是假绿。同样的轮次、同样的 prompt，然后对比两份 `friction.md`——只有新被
  测者的行变了，才算真修好。
- 判断一条提案看的是：它针对的卡点消失了，**而且没有引入新的一类**。一个缺陷换成另一个，总数上
  看起来像进步。
- **不要把 R2 的 prompt 写细。** "整张图统一调一下"没说调成什么色、也没说文档级还是节点级，这个
  模糊就是考题。skill 的职责是让**层级**变清楚（文档默认还是单个节点），不是替用户猜颜色。写成
  "用 `--default-tone warning`"就变成了拼写练习。
- **让被测者看不到分析内容。** 不要给上一轮的卡点表、不要给 owner 的讨论记录、不要在 prompt 或
  工作目录里放 issue 正文：一个读过"定位功能没被发现"的被测者会专门去找它，那样的运行什么都测不
  出来。
