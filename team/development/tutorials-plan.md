# 公开教程栏目计划

> 本文约定公开教程栏目怎么做：定位、目录、发布节奏和分工。
>
> 教程正文不写在 `team/`。发布后的文章放在仓库根目录的 `tutorials/`，和产品文档 `docs/` 分开，但随同一 GitHub Pages 站点一起发布。`team/` 仍然只对内，不进入站点。
>
> **状态**：规划中，待确认。
> **日期**：2026-11-26
> **负责人**：Mira（Project Manager）

## 1. 目标

为 jsMind v2 建立一个长期可积累的「教程 / Tutorials」栏目。文章同时承担三种作用：教人完成一件事、用完整例子展示能力、给推广提供可引用的素材。

它要解决的问题不是「API 怎么调用」，那是产品文档的事。教程回答的是：「我想做这件事，具体怎么做成。」例如用 Skill 画一张脑图、给节点加高亮、给小朋友讲一个主题、做一次市场调研。

## 2. 原则

- 和产品文档分开：不写入指南、设计、参考的侧栏。
- 和文档站一起发布：同一仓库、同一次 GitHub Pages 发布，首页能进入两边。
- 先简单，再沉淀：开始只维护一个栏目，用标签区分文章类型；合集等积累后再做。
- 中英文平行：栏目按两种语言建设，但不要求每一篇同一天双语齐活。
- 只写已经发布的 2.x 能力，标明 preview，不承诺尚未完成的功能。
- 质量先于篇数：模板和发布路径走顺之前，不追求每周固定产量。

## 3. 分工

| 角色 | 负责 |
|---|---|
| Mira（PM） | 规划栏目和站点结构；撰写教程正文；配图片、链接和示例文件；保证命令、Skill、API 与当前 2.x 一致 |
| Moka（Marketing） | 不负责写站点上的正文。文章发布后，拿到链接和素材，发到站点以外的渠道 |
| Holt（Coordinator） | 按团队流程安排相关 PR 的审查和终审 |
| 用户（hizzgdev） | 终审并合并 |

## 4. 仓库与站点结构

产品文档继续在 `docs/`，站点路径仍是 `/docs/`。教程是仓库根目录下的并列内容：

```
tutorials/
  assets/
    <编号>-intro.png
    <编号>-first-level-nodes.png
    <编号>-example.jm
  en/
    index.md
    posts/
      <编号>-how-to-build-a-mindmap.md
  zh/
    index.md
    posts/
      <编号>-how-to-build-a-mindmap.md
```

站点路径是 `/tutorials/`。语言规则与文档一致：入口按本地记录的语言跳转，没选过则默认英文；每种语言有自己的 URL（`/tutorials/en/`、`/tutorials/zh/`）；页面上可以切换语言。某一边尚未发布时，不要链到空页，应说明另一边还没有。

文章文件名不带日期，格式是「编号 + 英文 slug」，例如 `<编号>-how-to-build-a-mindmap.md`。编号至少写成三位，不足三位时补前导零；升到四位或更长完全可以，不必为此改规则。中英文使用同一编号和同一 slug，方便对照、切换，也方便口头指认某一篇或某一个文件。日期只写在 frontmatter 里，同时标注编号。栏目列表和首页「最近教程」按 frontmatter 中的日期排序，不依赖文件名。

第一篇文章的起始编号不在本文写死，写具体文章时再指定；之后按发表顺序递增。已经用过的编号不回收；即使后来标记为 deprecated，仍保持原编号和原地址。

示例脑图、截图和可下载文件默认放在共用的 `tutorials/assets/` 下，不再按文章分子目录。资源文件名必须以该篇编号开头，与文章编号保持一致，例如文章 `<编号>-how-to-build-a-mindmap.md` 引用 `<编号>-intro.png`、`<编号>-first-level-nodes.png`。中英文正文引用同一路径，不要按语言各放一份。不要把这些示例塞进 `docs/` 或 Playground 目录，以免和产品文档、Playground 自带示例混在一起。

如果某一语言需要不同版本的素材（例如案例文章里，脑图节点文字已经分成中文或英文），再在对应语言目录下建立 `assets_override/`，文件名与共用资源对齐：

```
tutorials/
  assets/
    <编号>-intro.png
    <编号>-example.jm
  zh/
    assets_override/
      <编号>-example.jm
```

只有内容确实不同的文件才放进 `assets_override/`，其余仍用共用文件。发布时在站点产出里做替换：先用共用 `assets/`，再用该语言的 `assets_override/` 覆盖同名文件。不要改写仓库里的共用原件。这个替换实现不必在栏目搭起来时就做，等第一篇真正需要分语言素材时再补；目录约定先按上面执行。起步不要预建空的 `assets_override/`。

`team/` 和 `AGENTS.md` 仍不发布。

### 首页

根路径的首页继续是产品入口，不改成文档目录，也不改成教程列表。首页同时放三个入口：**文档**、**教程**、**Playground**。可以再列出两三篇最近的教程，完整列表在 `/tutorials/`。安装说明、GitHub 和「目前是 2.x preview」仍留在首页。

## 5. 栏目形态

对外只开一个栏目，不再拆成「教程 / 案例 / 推广」三个入口。每篇文章打标签，起步用这两个即可：

- 技巧：只讲一个具体做法，例如给节点加高亮
- 案例：用一个完整场景走完，例如给小朋友讲宇宙大爆炸、做市场调研

等大约有 8 到 10 篇文章后，再做合集（例如「用 Skill 画脑图」「教学场景」「调研方法」）。合集是后来沉淀的，不在栏目上线时先行拆细。

## 6. 文章写法

每篇包含：

- 标题、编号、日期、标签。编号和日期都写在 frontmatter 里，例如：

```yaml
id: <编号>
date: YYYY-MM-DD
tags:
  - 技巧
```

- 适用版本：写 `2.x`，并标明当前是 preview，内容以后可能变
- 一两句说明这篇文章能做成什么
- 正文：目标、需要的准备、步骤、结果
- 图片、链接，以及可下载或可打开的示例文件

不写还没发布的能力。命令、参数和 Skill 用法必须和当时的产品文档一致。公开正文避免写死三位版本号（例如 `2.0.1`），版本规则仍按 [versioning-conventions.md](versioning-conventions.md)。

可以用一个很短的模板文件（例如 `tutorials/_template.md`），第一批文章按它写。不必一上来做复杂的内容系统。

## 7. 语言节奏

栏目和目录按中英文平行建设。写作时先完成更顺手的那一边，另一边尽快补上。允许一篇先上线一种语言，但要在语言切换处说清楚，而不是给死链。

对外推广时，Moka 使用已发布的那种语言的链接；双语都有之后，再按渠道选择。

## 8. 分阶段开展

### 第一阶段：把栏目搭起来

只做基础设施，先不上很多文章。

- 建立 `tutorials/en`、`tutorials/zh`、共用的 `tutorials/assets/` 和文章模板
- 接入现有站点的组装和 GitHub Pages 发布，使 `/tutorials/` 可访问
- 顶栏能进入「文档」和「教程」
- 首页加上教程入口，并预留「最近教程」的位置
- 语言切换、页脚（含 AI 协助说明）与文档站一致
- 补必要的站点测试：教程页能打开，且不进入产品文档的侧栏；`team/` 仍不发布

验收：打开网站能从首页进入教程栏目，中英文入口成立，文档站原有路径不受影响。

### 第二阶段：先写三篇

用第一批文章把模板和发布路径跑通：

1. 用 Skill 从零画出一张脑图并导出
2. 一个具体能力（建议：给节点加高亮或颜色）
3. 一个完整场景（教学或调研，先做其中一篇）

每篇带示例文件和必要截图。中英文按第 7 节的节奏补齐。发布后把链接交给 Moka。

验收：三篇文章在 `/tutorials/` 可阅读，示例能跟着步骤复现，产品文档无回归。

### 第三阶段：稳定更新

模板和发布路径走顺之后，再按大约每周 1 到 2 篇积累。不必为了凑数而写。产品有变更时，回看已发布文章：仍能用的及时改正文，已经不适用当前版本的标为 deprecated，不要删文件、改编号或改地址。

### 第四阶段：合集与 Playground

文章积累到大约 8 到 10 篇后，开始做合集页。

另外规划 Playground 的增强：用地址参数加载教程里的示例文件，文章中提供「在 Playground 中打开」。第一批文章先把示例文件放进 `tutorials/assets/`，不必在栏目上线时同时改 Playground。

## 9. 日常工作流

1. Mira 选定题目，确认它只用到已发布的 2.x 能力，并分配编号。第一篇的起始编号在写该文时再指定，此后递增。
2. Mira 撰写正文、配图和示例，按纯文档变更开 PR：建议标签 `documentation` 和 `hubie`，不必为每一篇文章单独开 Issue。基础设施（站点接入）单独一个 PR；之后文章可以一篇或一小批一个 PR。
3. 走现有团队审查，由用户终审后合并。
4. 站点发布后，Mira 把正式链接交给 Moka，由 Moka 向站外分发。
5. PR 上不要 @mention。

基础设施和文章不要混在同一个大 PR 里，除非改动很小。

## 10. 维护

- 教程依赖 Skill、CLI 和产品文档中的说明。这些一变，相关教程要一起检查。一篇文章是否已不适用于当前版本，起步靠这种手动检查；以后如果需要，可以另做一套检测机制，现在不先做。
- 预览版期间，每篇都保留「适用 2.x、内容可能变化」的提示。
- 已经发布的文章默认不撤下，以免站外链接失效。如果只是因为版本更新而不再适用于当前 2.x，应在 frontmatter 中标记为 deprecated（例如 `deprecated: true`，若有替代文章可同时写 `replaced_by` 编号），保留原编号、原文件和原地址，并在文首说明过时原因、必要时指向新文。栏目列表中可以继续出现，但必须明确标出 deprecated，避免读者按旧步骤操作。
- 只有在涉及敏感信息、法律原因等确实不能再公开时，才考虑从栏目撤下。即便如此，也应尽量在原地址保留说明页或跳转，而不是直接 404。对内若需留存原稿，再放入 `team/archive/`。

## 11. 本文的位置

本文放在 `team/development/`，由 PM 维护。发布教程栏目、调整节奏或分工时，更新本文，而不是另起一份平行计划。

对外教程在 `tutorials/`，分工写在 `team/README.md`；本文只保留对内计划。
