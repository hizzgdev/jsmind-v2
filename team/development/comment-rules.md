# 注释取舍

> **本文是「这一行注释要不要存在」的唯一约定。** 别处只指向这里，不复述 —— 依据是
> [`commit-types.md`](commit-types.md) 开头那条：同一条规则写在两个文件里，其中一个会漂。

## 0. 先分清：陈述还是指路

- **陈述**：断言代码或外部世界是什么样、必须怎么样。它可能变假。
- **指路**：只告诉你「下面这一段是干什么的」，不承诺任何东西。它不会变假，只会失效
  （标签和代码挪开了）。

两种都允许，标准不同：陈述要按 §1 过关，指路只要跟着代码走（§2）。

## 1. 允许的陈述

1. **约束，且能指出违反它的后果。** 写清「因为什么，否则会怎样」：测试名、CI 检查、运行时报错都算后果。
   指不出后果的不是约束，是愿望 —— 愿望会随下一个人对代码的理解一起变。
2. **代码里读不出来的事实。** 外部 API 的怪行为（空结果返回 204 而不是 200）、浏览器与字体的差异、
   v1 当年怎么做的。测试够不到外部世界，类型系统也表达不了这些。
3. **位置标记。** `---- cycles ----`、字段表的分节标题：不陈述任何事实，归类上更接近指路，
   留着当索引。

## 2. 指路：允许，但带着义务

`// Validate destination options`、`// Get target parent`、`// Emit event`、`1.` / `2.` 这样的步骤编号，
是给长方法做的目录：扫一眼就知道这一段在干什么，改的时候知道该在哪一段动手。这类注释是本仓库的
既有风格，**保留**。

义务只有一条：**代码动了，标签跟着动。** 挪走一段忘了挪标签、删掉一段留下标签，都是让索引开始说谎
—— 这时候它不是「多余的注释」，是错的注释。删掉对应代码时，把它的标签一起删。

## 3. 要删的两种

- **变更叙事。** `// 改成…`、`// 修复了…`、`used to`、`no longer`。那是 commit message 的活；
  进代码就变成「当时的对话记录」，而且代码再动一次它就假一半。
- **声称做到了但没做的事。** `// 校验输入` 挂在一个没有校验的函数头上。这一类比没有注释更坏：
  它把「没做」读成「做了」。

## 4. 判定问题

**这条注释在陈述还是在指路？**

- 指路 → 留，检查标签还贴着它描述的那段代码。
- 陈述 → 它能不能指出违反它的后果，或者说出一个代码里读不到的事实？能 → 留；不能 → 删。

为什么陈述要这么严：读者会拿陈述去做决定，而陈述的验证成本高 —— 「这段不能删」在代码里看不出来。
过期那一项有数据撑着：注释与代码不一致的变更，引入 bug 的概率约为一致变更的 1.5 倍，刚产生不一致
时最高（[arXiv 2409.10781](https://arxiv.org/abs/2409.10781)）。证据支持的是「让注释跟着代码走」，
不是「不写注释」：删掉约束，约束不会消失，只是从可见变成不可见。

## 5. JSDoc 不是豁免区，但有额外成本

挂在 `export` 上的 JSDoc 是 API 文档的输入（`dist/jsmind.d.ts` → `npm run docs:api`），改它要同步
`scripts/docs/api-translations-zh.json`，否则生成时缺中文条目会直接抛错。改这类注释时把这两步当
一个动作。

挂在内部成员上的 JSDoc 不进 `.d.ts`，按 §0–§4 处理，没有豁免。

`@public` / `@remarks` / `Since:` 这些标记是文档管线的输入或版本约定的载体，不属于「可删的措辞」。

## 6. 测试不豁免

测试里的注释多数是「这个用例为什么用这份 fixture」，属于 §1 第 2 类；用例分组的标签属于 §2，
保留并跟着用例走。

## 7. 执行

靠评审，不加自动闸门。正则能匹配「之前」「used to」，但分不清指路和陈述，误报会逼作者改写措辞
而不是改掉废话 —— 与 `commit-types.md` §3 拒绝「类型对 diff」的闸门是同一个理由。
