# CI 里让人看得见的验证

**一个功能做完，CI 要能自动交出一个「人可以消费」的结果。**

断言能证明算对了；断言证明不了结果看起来像东西，也证明不了产物拿出去能不能打开。这两件事没人替你看，所以要么由人肉点，要么由 CI 产出一个能看的东西。本文记这条链子的分层和理由。

**机制不在这里。** 怎么发、发到哪、secret 叫什么、失败怎么处理，写在 `.github/workflows/ci.yml` 对应步骤上方的注释里——离会漂的代码最近的注释最不容易漂。本文回答的是「为什么是这几层、每层证明什么、下一代往哪走」。

## 1. 和兄弟文档的分工

| 文档 | 管什么 |
|---|---|
| [ci-classification.md](ci-classification.md) | 哪些检查拦合并、哪些只是信息 |
| [render-test-plan.md](render-test-plan.md) | 渲染层该有哪些断言、断言什么值 |
| 本文 | 除了断言，CI 还要产出什么给人看；人看到的东西怎么变成机器检查 |

## 2. 四层

| 层 | CI 产出 | 证明什么 | 不证明什么 | 现状 |
|---|---|---|---|---|
| 断言 | 通过 / 失败 | 几何、数据、序列化算对了 | 看起来对不对 | 有 |
| 看图 | 一张 PNG，贴在 PR 上 | 布局不歪、节点不重叠、文字不溢出 | 产物能不能打开、有没有交互 | 有 |
| 看网页 | 一个链接，点开就是这一版产物 | 产物在真实浏览器、真实网络下能打开、能滚 | 交互是否真的工作 | #226 |
| 在线 e2e | 浏览器脚本操作那个链接 | 交互也工作 | 好不好看 | 计划 |

## 3. 看图：一张 PNG 能证明什么

做法：同一份 prepared data → `jsmind export image` → PNG → 上传成 comment 附件 → 贴进带隐藏 marker 的 comment。

三个设计选择值得记住：

- **图片而不是 SVG。** GitHub 会过滤 SVG 里的脚本与外链，也不给内联样式自由；PNG 是唯一能保证"贴上来就是这样"的格式。
- **透明背景。** 图在浅色和深色主题下都能看，不需要发两张。
- **comment 带 marker、删旧贴新。** 否则每次 push 都往上堆一张图，读者看到的是一列历史上已经不对的画。

它擅长的是人眼一秒能扫出来的错：节点重叠、连线错边、文字溢出边框、整体单边偏。这些恰好是断言最不擅长描述的——断言能说"两个矩形不相交"，说不出"这张图看着是塌的"。

它证明不了的：产物能不能打开、交互能不能用、字体回退后长什么样、视口外的东西。

## 4. 看网页：一个链接比一张图片多证明什么

做法：同一份 data → `jsmind export html` → 单个自包含 `.html` → 发一个 surge revision → URL 写进同一条 comment。

- **为什么不贴附件。** 试过：GitHub 的 user-attachments 对 html 要么拒绝、要么退化成"登录之后下载一个文件"。一句"点开看看"变成四道关，等于没做。
- **为什么单域名 + 每版一个 revision。** surge 每个域名保留最近 100 个 revision，更早的自动淘汰。于是"定期删掉旧预览"这件事不存在——它由数量边界自动完成，不需要 teardown，也不需要每个 PR 一个域名。
- **为什么产物必须自包含。** 这个页面存在的意义是"零外链、断网可开"。如果它引用 CDN，那预览证明的就不是产物本身，而是一个恰好能联网的页面。

它比图片多证明的，恰好是图片结构上做不到的：`content-type`、编码、压缩、路径大小写、CDN 缓存——这些只在"发布出去"之后才暴露。`file://` 打开成功不代表 `https://` 打开成功。

它仍然不证明交互：人可能只滚一下就走。

## 5. 在线 e2e：把人的一次观察变成机器检查

现有的 `__tests__/ui/export-html.test.ts` 已经用真 Chromium 打开 `file://` 的产物，断言节点数和尺寸。它证明"构建出来的文件在本地能用"。

它不证明"发布出去的那一份能用"：`content-type`、gzip、CDN 缓存、路径大小写、CSP、混合内容，全都在发布之后才出现。所以下一步是：在部署之后，用浏览器脚本打开那个 URL，跑一遍真实交互。

要断言什么（等页面有了这些功能再写）：

- 页面加载完成、节点数正确——这一条现在就能写
- 平移与缩放的坐标变化、居中复位
- 折叠与展开后的子节点数
- toolbar 的每个按钮真的改变了状态

**什么时候值得做**：等 S2 / S3 那些交互落进去、人肉点一眼开始漏东西的时候。在那之前，它是给一个还没长功能的东西写脚本，为时过早——这条判据写在这里，免得以后有人凭"应该要有 e2e"就开工。

**放在哪里**：先不进 required。外部服务（surge、CDN）的偶发失败会让门变脆，而一个偶发红门会训练所有人忽略它。先 nightly 或手动触发，稳定一段时间后再讨论要不要进 PR。

## 6. 四条原则

1. **昂贵的东西不进合并门。** 浏览器、token、外部服务失败的代价是信息，不是阻塞。拦合并的只有 `ci-classification.md` 里那四个 required。
2. **产物要长成人能直接消费的样子。** 图在 comment 里，页面在链接后。一个验证如果需要 reviewer 下载、解压、找文件，它的成本就从 CI 转嫁给了人。
3. **同一件事的多个视图必须来自同一次构建、同一份输入。** 图和页面共用 `tmp/preview-data.json`；否则两幅画描述的是两次不同的运行。
4. **给人看的，迟早要变成机器看的。** 人眼是探针的第一版，脚本是第二版；每一次人工观察都在指出"这条以后该自动断言"。

## 7. 失败策略

| 层 | 失败时 |
|---|---|
| 断言 | 红，拦合并 |
| 看图 | 不拦。comment 照发，写明图片不可用 |
| 看网页 | 不拦。comment 照发，写明预览不可用，图仍然贴 |
| 在线 e2e | 先只报告，观察一段时间再决定 |

关键在于别让"看不见"变成静默：任何一层失败都要在 PR 上留一句话，否则读者会以为这个功能根本不存在。
