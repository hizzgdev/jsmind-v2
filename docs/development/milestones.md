# jsMind v2 Milestones

> 这份文档回答「先做什么」，`roadmap.md` 回答「每一层怎么做」。
> 两份都有效：milestones 排优先级和验收标准，roadmap 存技术细节和已知的坑。
> 编号对应关系见附录 A。

## 0. 为什么重新划分

原来的 S1–S13 是按**层次**排的：数据 → 渲染 → 产物 → 交互 → Agent 接入。

工程上没问题，但它不是按**谁先受益**排的。按层次推进的结果是：
数据层、渲染层、产物层各自都完成得很好，而唯一真正验证「这东西有没有用」的
环节 —— agent 端到端画一张图 —— 排在最后。

**这个项目的目的不是做一个画图库，是让 agent 能画脑图。**

所以改成按受益者排序：

| | 受益者 | 一句话 | 判定 |
|---|---|---|---|
| **M1** | Agent | 从一句话到一张可用的图 | 没有它，项目没有存在的理由 |
| **M2** | 用户 | 拿到一个能打开、能看的成品 | 没有它，agent 画完了没人看得见 |
| **M3** | 做得更好的人 | 编辑、插件、生态 | 没有它也能用 |

**这个顺序的硬约束**：M1 没跑通之前不做 M2，M2 没跑通之前不做 M3。
理由是每一层都在验证上一层的前提 —— 如果 agent 画不出像样的图，
给用户做一个精致的查看器没有意义。

## M1 · Agent 能用

### 目标

**agent 从一句自然语言需求，做出一个结构合理、视觉可读、经过自检的脑图文件。**

不含 UI 编辑 —— agent 不需要。也不含用户侧交付 —— 那是 M2。

### 验收标准

> 给一个主题（例如「给我画 jsmind 的架构脑图」），agent 只用 CLI，
> **全程不手写 JSON**，产出 .json + .png，并且：
> 1. 结构上 `validate` 通过
> 2. agent 自己出图看过至少一次，并根据看到的问题做过调整
> 3. 最终产物能被人直接看懂（文字不挤压、层级清晰）

第 2 条是 M1 的核心，也是这个项目区别于「一个画图库」的地方。
UI 测试和导出能力都是为它服务的。

### 任务清单

#### M1.1 · `node set-style` —— 补齐表达能力的最后一块 ✅

现在 CLI 能改结构、文字、折叠、换边、移动，**唯独不能改样式**。
而 `JmNodeStyle` 里有 `tone` / `fontSize` / `fontWeight`，这些是 agent
表达「这是风险节点」「这是重点」的唯一手段。

- [x] CLI 接口设计：`jsmind node set-style <file> --node-id <id> [options]`
- [x] 支持的字段：`--tone` / `--font-size` / `--font-weight` / `--background` / `--color` / `--border-color` / `--border-width` / `--border-style`，外加 `incoming.*` 的四个（`--incoming-color` / `-width` / `-pattern` / `-curve`）
- [x] 值的合法性校验：枚举值在 CLI 层拦（报错点名 flag），数值与 schema 规则一致（正数），颜色只要求是字符串
- [x] 清除语义：`--clear <字段列表>`（camelCase 和 kebab-case 都认）+ `--reset`（清空整个 style 块）
- [x] 单测：20 个用例覆盖合法值、非法值、清除、嵌套字段、空 style 回收、dry-run
- [x] `docs/requirements/v2-cli.md` 补 §3.3 命令说明
- [x] `--dry-run` 和 `--json` 行为与其他 `node` 子命令一致

**实现时改了一处设计**：参数校验移到了读文件之前。原本校验发生在 `runMutation` 的回调里，意味着一个拼错的 flag 要先读完文件、建好临时副本才报错 —— 文件不存在时更会报成 IO 错误而不是用法错误。现在拆成 `parseStyleArgs`（纯参数）和 `applyStyle`（合入当前 style）两步。

**注意**：roadmap S7c 里曾写「前置是 `onNodeUpdated` 必须接通」——**那句是错的**。
`onNodeUpdated` 只影响浏览器里的实时重绘；CLI 改文件后重新 export 是完整重建，
不经过更新路径。这个命令不依赖任何未完成的东西。

#### M1.2 · `context` 看得见样式 —— 修掉 agent 的盲区

现在 `context` 只输出 `id` / `level` / `text`。agent 改了 `tone` 之后，
**它看不见自己改了什么**，只能出图用视觉确认，而视觉确认是有成本的。

- [ ] 决定默认行为：是默认显示 `tone`，还是 `--style` 才显示
- [ ] 显示 `folded` 状态（折叠的子树在 outline 里怎么体现）
- [ ] `--json` 输出里对应字段的名称和位置
- [ ] 考虑 `side` 要不要显示（agent 排布左右分支时有用）
- [ ] 单测
- [ ] 文档更新

**设计权衡**：`context` 是 agent 每次操作都要跑的「眼睛」，输出越短越省 token。
样式信息全塞进去会让每行变长。倾向的做法是**只显示非默认值** ——
没有 `tone` 的节点不加字段，这样常规结构查询的输出不变长。

#### M1.3 · Skill —— 把能力变成流程

roadmap 第 8 节已经把机制设计清楚了（三档强度、下沉到 CLI、
「凡是结果必须确定的事情都不许写进 skill」）。这一项是把它写出来。

- [ ] 决定 skill 的载体和位置（仓库内 `skills/jsmind/SKILL.md`？还是独立分发）
- [ ] 决定 skill 的格式（是否跟随 Hermes / Claude skill 的约定）
- [ ] 写主流程：`context` 找 id → `mind`/`node` 改 → `validate` 查 → `export` 看
- [ ] **写检查清单**：什么情况下必须出图看一眼
      （不是「记得检查」，是明确列出触发条件）
- [ ] 写看完之后怎么办：文字挤 → 改什么；层级乱 → 改什么
- [ ] 禁止事项：不许直接写 JSON（绕过校验）、不许绕过 `jsmind` 命令
- [ ] 一个完整的示例会话（从需求到成品，带命令和输出）

**待定的设计问题**（做的时候定）：
「看一眼」是 agent 的自觉还是流程的一部分？
- 自觉：写进检查清单，简单场景不浪费成本，但可能被跳过
- 流程：强制每版都看，可靠但两个节点也要出图，成本高

#### M1.4 · agent 视角的 E2E

现有的 UI 测试验证的是「渲染不崩」，不是「agent 能不能完成任务」。

- [ ] 一个脚本，模拟 agent 的完整路径：
      建图 → 加 N 层节点 → 改样式 → 校验 → 出图
- [ ] 断言：退出码全 0、`validate` 通过、PNG 生成且尺寸合理
- [ ] 放进 CI 的 `ui` job（需要浏览器）
- [ ] 记录单次全流程耗时（74ms/命令，20 个节点约 1.5s，作为回归基线）

**这一项不做视觉断言** —— 「图好不好看」交给 agent 运行时判断，
CI 只保证「流程能跑通、产物能生成」。

### M1 明确不包含

- 浏览器里的实时重绘（`onNodeUpdated` / `onNodeMoved`）—— 那是 M3 编辑需求
- HTML 产物 —— M2
- 自定义渲染器 —— M3
- MCP server —— M3
- 任何 UI 编辑能力

### 分阶段落地

不是一个 PR 做完。按依赖排：

| 阶段 | 内容 | 前置 | 独立可验证 |
|---|---|---|---|
| **①** | M1.1 `node set-style` | 无 | CLI 能改样式，单测绿 |
| **②** | M1.2 `context` 显示样式 | ①（要先能改，显示才有意义） | agent 能看见自己改的样式 |
| **③** | M1.3 Skill | ① ② | 一个真人按 skill 走一遍能出图 |
| **④** | M1.4 E2E | ① ② | CI 里跑通全流程 |

②理论上可以先做，但先做 ① 更顺 —— 否则是给一个改不了的东西加显示。

③ 放最后是因为写 skill 的过程会暴露 CLI 缺什么，那时回头改比现在猜准。

## M2 · 用户能用

### 目标

**用户拿到一个能双击打开、能看、能交互的成品。**

### 为什么核心是自包含 HTML，不是编辑器

用户现在拿到的东西是：一张 PNG（只能看），或一个 .json（打不开）。

所以「用户能用」的最低门槛不是编辑，是**能打开一个交互式的图**。
这正好是 roadmap S8，而它在原 S 序列里排第 8 —— 位置靠后但不该靠后。

### 任务清单

- [ ] S8 自包含 HTML 产物（JS + 数据内联，断网可开）
- [ ] S14 查看器平移 / 缩放 / 居中
      —— 比屏幕大的图不能平移等于看不全，所以这是 M2 的一部分，不是「高级功能」
- [ ] S9 的 HTML 部分（PNG 已完成）
- [ ] 产物在主流浏览器里打开验证（不只是 headless Chromium）

### M2 明确不包含

- 节点编辑（拖拽、双击改字）—— M3
- 协作、版本控制

## 附录 B · 判断标准

以后往清单里加东西时，先问三个问题：

1. **它是为谁做的？** —— 加不进 M1/M2/M3 任何一格的，都是自嗨
2. **它的验收能不能一句话说清？** —— 说不清的，说明还没想明白
3. **它挡不挡别人的路？** —— 不挡的，往后排

还有一条从 roadmap 第 8 节继承来的：

> 凡是结果必须确定的事情，都不许写进 skill。
> 确定性的东西全部下沉到代码；skill 只描述意图和顺序，不描述如何正确。
